# Pi Plugin Audit — old Orchestra extension (read-only reference for Step 11)

Source: `/Users/james/workspace/orchestra/extensions/pi/orchestra/index.ts` (1,916 lines; single file, no other files in the directory). Read against `orchestra2/SPEC.md` and `PLAN.md` phase 11. No old code copied or modified.

Architecture in one sentence: the extension is a **thin host adapter around the `orchestra` CLI** — nearly every operation spawns `orchestra <subcommand>` (many are `_`-prefixed private commands fed JSON via stdin), while the extension owns only host-native concerns: tool/command registration, UI widgets, watchers, budget hooks, and `pi.sendUserMessage` delivery.

---

## 1. TOOLS

Two tools, registered at startup (`refreshOrchestraToolRegistrations`, index.ts:1782-1786), with descriptions/parameter text loaded from core via `orchestra _tool-info` (index.ts:536-545) — prompt copy lives in core, not the extension.

### `orch_dispatch` (index.ts:1745-1765)
- Parameters: `goal` (required), `additionalContext`, `role`, `taskLabel` (all optional). `timeout` is explicitly rejected ("orch_status-style dispatch timeout is not supported on the tool", index.ts:1748-1750).
- Behavior: `normalizePiSessionId(ctx.sessionManager.getSessionId())` → `dispatchWorker(...)`. Returns a text tool result with the dispatch ack (or error).
- Returns: dispatch acknowledgement + guidance text from `orchestra _dispatch-ack --run-id <id> --role <role>` (index.ts:1093).

### `orch_status` (index.ts:1639-1743)
- One tool with an `action` union: `on | orchestrate | status | history | help | doctor | roles | stop`; optional `limit`, `runId`, `role`, `setting`, `value`.
- Each action shells to the corresponding CLI command: `help-host`, `doctor`, `_session-mode set`, `status --json`, `history --limit`, `roles --all`, `stop --session-id --run-id`.
- `roles` is **read-only** through the tool (writes rejected, index.ts:1712-1714) — role setting changes are command-only.
- `stop` refreshes the footer status after stopping.

Gated registration: if env `ORCHESTRA_DISPATCH_BUDGET=1`, `orch_dispatch` is not registered at all (index.ts:229-232, 1775-1777) — a per-process dispatch kill-switch.

Core coverage: tool *descriptions* are core-supplied (`_tool-info`); dispatch/ack semantics map to built `submit.py`/`dispatcher.py`. **Gap:** the `_tool-info`-style metadata endpoint and the ack/guidance text generation do not yet exist in orchestra2 core; acknowledgement guidance in SPEC ("dispatch acknowledgement and guidance") will need a core source.

## 2. SLASH COMMANDS

One command, `/orch <subcommand>` (index.ts:1786-1915), with rich tab completions (`getOrchArgumentCompletions`, index.ts:1494-1625) covering subcommands, role names, harness configs, `enabled true/false`, timeout values, and active run ids for `stop`.

Subcommands (each shells to CLI unless noted):
- `help` / bare `/orch` → `orchestra help-host` (index.ts:1800-1808)
- `on` / `orchestrate` / `off` → `_session-mode set --mode X --json`, applies `effect.tools_enabled` via `setOrchestraToolsActive` (index.ts:1462-1487, 1809-1823)
- `doctor` → `orchestra doctor` (1824-1827)
- `config [KEY] [VALUE]` → `orchestra config ...` (1829-1832)
- `roles ...` → `orchestra roles ...`; on success invalidates the 5s role-metadata cache and re-registers tools (1834-1843)
- `status` → human output via `status`, plus `--json` parsed to update the cached status and footer widget (1845-1857)
- `history [limit]` → `orchestra history --session-id --limit` (default 10) (1859-1870)
- `stop <run-id>` → `orchestra stop --session-id --run-id`, refreshes footer (1872-1883); tab completion lists active run ids
- `do [--role R] [--timeout SEC] [--task-label L] <goal>` → `parseDoArgs` (a hand-written shell-style tokenizer, index.ts:610-690) then the same `dispatchWorker` path as the tool (1885-1909)
- unknown → warning + help (1911-1913)

Echo rendering: the invoked command is echoed as a custom `orchestra-command` entry, generated by core via `orchestra _command-echo <args>` (index.ts:531-534, 1788-1791) so core owns canonical echo text.

**Simplification opportunity (owner favors this):** the completion engine (~130 lines), the tokenizer, `--task-label`/`--timeout` flag parsing, and `commandEchoText` exist solely for `/orch do` and `/orch roles`. A Phase-1 slice of `help | do | status | history | stop` (dropping `roles`, `config`, `on/off/orchestrate`, `doctor`, and tab completions) removes most of the command-layer complexity while keeping the full dispatch journey. Mode and roles/config commands can return later as plain pass-throughs.

## 3. UX

- **Footer widget** (`orchestra`, placement `belowEditor`, index.ts:145-172): token accounting (`↑in ↓out Rreasoning CH% -$cost`), `(Orchestra:<mode>)`, and an active-worker role meter (role name rendered with N active letters bolded, remainder dimmed — index.ts:41-57). Cost is recomputed against the main model via `calculateCost` from `@earendil-works/pi-ai` (index.ts:83-109). Hidden in mode `off`.
- **Status refresh machinery**: 2s status cache (index.ts:1396-1408), per-session generation counters and refresh-request ids to discard stale async updates (index.ts:843-880), fresh-refresh option after every state change.
- **Progress notifications**: per-run `_await-run` watcher spawns `orchestra _progress-message --completed N --total M --run-id --status --role` and surfaces it via `ctx.ui.notify` (index.ts:926-1050).
- **Entry renderers**: `orchestra-command` (echoed slash command) and `orchestra-output` (toolOutput-themed text) custom entry types (index.ts:792-815).
- **Non-UI fallback**: everything falls back to `process.stdout`/`stderr` writes when `ctx.hasUI` is false (index.ts:193-203, 805-815, 862-868).

Core coverage: none needed — this is all host-native. But note the footer depends on `status --json` payload shape (`active_runs`, `role_counts`, `accounting`) — a core status contract orchestra2 must eventually expose or deliberately drop.

## 4. DELIVERY (the most complex subsystem)

End-to-end return-to-originating-session flow:

1. **Report watcher** (`watchSessionReport`, index.ts:1145-1254): spawns `orchestra _await-session-report --session-id <id> [--run-id <id>] --json`. On close with exit 0, parses `{ runIds: [...], report: "..." }` and stores a `PendingSessionReport`.
2. **Retry policy**: up to 3 attempts, backoff 500ms×(attempt+1), re-spawning the watcher (index.ts:1104-1120, 1236-1253).
3. **Injection** (`submitPendingReport`, index.ts:1122-1141): `pi.sendUserMessage(pending.message, { deliverAs: "steer" })` — the report is delivered as a *steered user message* into the live orchestrator conversation.
4. **Delivery confirmation** (`pi.on("message_end")`, index.ts:1256-1291): when the model's context echoes the exact pending message text back as a user message, the extension calls `orchestra _mark-session-report-delivered --session-id --run-id ...` so core won't redeliver, then deletes pending state and re-arms the watcher if more reports may come (`watchAgain`).
5. **Compaction safety**: `session_before_compact` marks the session compacting; `session_compact`/`session_compact_failed` schedule delivery on a 0ms timer after the lifecycle callback returns (index.ts:762-792) — avoiding delivery into a compacting context.
6. **Session lifecycle**: on `session_start`, if `status --json` shows `session_report_available` or active runs, a watcher is armed immediately so reports survive host restarts (index.ts:1293-1334). On `session_shutdown`, watchers are killed and pending state cleared (index.ts:1336-1345). Per-session *generations* (bumped on start/shutdown) discard all stale watcher callbacks (index.ts:848-861).
7. **Unconfirmed reports are dropped locally, not consumed** — runs stay unreported so a later watcher redelivers (index.ts:1355-1357 comment).

Core coverage: **partial.** Built `results.py` (`assemble`) produces the consolidated return, and SPEC's delivery/restart-recovery baseline is defined, but there is no core "await session report / mark delivered" API yet — the durable report queue, idempotent delivery marks, and redelivery-on-restart semantics are **new core capability** (or plugin-owned state). This is the single biggest uncovered behavior.

## 5. EXECUTION

- The extension never launches agents itself. `dispatchWorker` (index.ts:1060-1136) spawns `orchestra do --session-id <pi:X> --goal <goal> --json [--additional-context] [--role] [--timeout] [--task-label] [--parent-context-artifact -]`.
- **Parent context**: if the resolved role is in `_role-metadata`'s `passParentContext` list, the extension serializes Pi session messages (`sessionManager.buildContextEntries()`, falling back to `getBranch()`, falling back to a goal/role/label stub) to text and pipes it on **stdin** (`--parent-context-artifact -`); no temp files (index.ts:452-504, 1077-1090).
- **Model resolution, argv for the actual agent run, env, SPSI injection into the subagent, transcript location**: all inside the `orchestra` CLI, invisible to the extension. The extension's only execution concerns are the child CLI process and watcher lifecycles.
- Progress watching uses the dispatch's `timeout_seconds` + 30s margin to kill the `_await-run` watcher (index.ts:926-950).
- **Malformed-ack recovery**: if `orchestra do` exits 0 but no `run_id` parses, the extension arms a session-level report watcher and tells the model not to redispatch (index.ts:1105-1114).

Core coverage: **strong.** `shell.py`, `harness.py`, `submit.py`, `artifacts.py` (`_capture_parent_context` exists), and `dispatcher.py` cover execution, assignment, and context capture. The plugin's job is reduced to: build the core submission request, spawn one process, and read its JSON ack.

## 6. IDENTITY / SESSION

- Session id: `pi:${ctx.sessionManager.getSessionId()}` — always from **runtime context**, never prompt text (index.ts:235-240, 1647-1653, 1796). `before_agent_start` falls back to the last `session_start` id if the manager throws (index.ts:1418-1427).
- Runs↔sessions: in-memory `sessionRuns`/`sessionCompletedRuns` maps plus core-side `--session-id` on every CLI call (index.ts:823-834).
- Modes: `off | on | orchestrate` (`MainSessionMode`), initialized from `_tool-info` at session start (index.ts:1322-1329), transitions through `_session-mode set` whose JSON `effect` carries `display_text`, `mode`, `tools_enabled`, `error` (index.ts:1452-1487). `setOrchestraToolsActive` adds/removes `orch_status`/`orch_dispatch` from `pi.getActiveTools()/setActiveTools` (index.ts:1748-1760 region: 1698-1712).
- Tool gating: `ORCHESTRA_DISPATCH_BUDGET=1` suppresses `orch_dispatch` registration entirely (index.ts:229-232).

Core coverage: **partial.** SPEC requires runtime-context identity and off/on modes; `config` exists. The mode-transition `effect` contract (tools_enabled + display text) is a core capability to define.

## 7. BUDGET / WRAP-UP

Entirely extension-side against the *orchestrator's own* pi run (not the subagent):

- Env: `ORCHESTRA_TURN_BUDGET` (turn count), `ORCHESTRA_SOFT_TIMEOUT_SECONDS` (wall clock from `sessionStartedAt`), `ORCHESTRA_BUDGET_EXCEEDED_PROMPT` (the wrap-up text, supplied externally) (index.ts:9-12, 726-744).
- `turn_end` hook decrements the turn budget, persists the decrement back into the env var, and at the last turn injects the wrap-up prompt once via `pi.sendUserMessage(..., { deliverAs: "steer" })` (index.ts:736-760).
- `tool_call` hook blocks in-flight tool calls once soft timeout is exceeded, with a core-supplied block reason (`softTimeoutBlockReason` from `_tool-info`) (index.ts:786-791).
- One-shot guard `budgetPromptInjected` prevents duplicates.

Core coverage: **partial.** `harness.py` has `Budgets` for *subagent* budgets; the SPEC budget-exhaustion flow ("budget guidance tells it to stop…") assumes the subagent-side mechanism (old orchestra presumably injects via env into the dispatched pi). **Gap:** the orchestrator-side turn/soft-timeout steering hooks are host behavior with no core counterpart; decide whether Phase 1 keeps them (recommended: defer) or needs a core-supplied wrap-up prompt.

## 8. CANCELLATION / STOP

- `/orch stop <run-id>` and `orch_status {action:"stop", runId}` → `orchestra stop --session-id <id> --run-id <id>`; footer refresh after (index.ts:1715-1737, 1872-1883).
- Ownership: stop requires the caller's `--session-id` to match the run's owning session (enforced by core).
- Process-group termination of the actual agent process is inside the CLI/dispatcher, not the extension. Watcher child processes are SIGTERM'd on session shutdown (index.ts:883-903).
- Tab completion of stoppable run ids comes from live `status --json` (index.ts:1519-1537).

Core coverage: **partial** — dispatcher has `_terminate_quietly`; a session-owned stop operation with ownership checks is needed as a core operation (submit/dispatcher-side) before the plugin can expose `stop`.

## 9. OTHER

- **Doctor/help**: pure pass-through to CLI (`help-host`, `doctor`) — core-owned diagnostics (index.ts:1673-1681, 1824-1827).
- **Role metadata cache**: 5s TTL on `_role-metadata` (roles, harnessConfigs, passParentContext, defaultRole) (index.ts:1360-1384); invalidated after `roles` writes.
- **Error-envelope parsing** (`parseCoreErrorEnvelope`, index.ts:560-600): shared JSON error shape `{kind:"error", ok:false, error:{message, operation, run_id}}` with graceful fallback to raw stderr/stdout — a reusable core↔plugin contract worth standardizing in orchestra2.
- **Telemetry**: none in the extension. **Config updates**: pass-through only.

## Proposed Phase-1 plugin slice

Owner intent: execution + `orch_dispatch` tool + delivery first; simplified slash commands.

1. **Core prerequisites (small)**: (a) a submit-ack JSON response (run id + ack/guidance text) from `submit.py`; (b) a durable per-session report store with "await pending report" and "mark delivered" semantics (can be plugin-owned files read by core, or core ops — recommend core ops for restart recovery); (c) a shared JSON error envelope.
2. **Plugin slice** (single file, mirrors old structure): session id from `ctx.sessionManager`; `orch_dispatch` tool → spawn orchestra2 CLI submit → register a report watcher that injects the report via `sendUserMessage(steer)` and marks delivered on echo; footer widget optional (defer the token/cost meter).
3. **Commands**: `/orch do` and `/orch status`/`history` only; plain argument string passed to a core `do` op (no tokenizer, no tab completions, no echo-entry rendering). Defer `roles`, `config`, `on/off/orchestrate`, `doctor`, `stop`, budget hooks, parent-context piping, and the dispatch-budget kill-switch to later slices.

Estimate: old extension is ~1,900 lines; the Phase-1 slice is roughly 300-400 lines of host code plus the three small core contracts above.
