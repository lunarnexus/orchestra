# Plan

## Goal

Add public, opt-in, machine-readable JSON output for every Orchestra CLI/helper path that host plugins use for protocol/control-flow decisions, preserve existing prose output for users and host UI, migrate plugins to consume JSON for structured fields, and clean up asset source-of-truth so root assets are canonical.

## Acceptance Criteria

- Existing human-readable CLI output remains the default and is covered by regression tests.
- JSON output is opt-in per command via `--json`; no global mode is required.
- JSON output is generated by Python core code, not by LLM/subagent prose.
- JSON contracts include stable fields needed by plugins; plugins no longer regex/prose-parse those fields.
- Host-visible messages remain equivalent to current behavior unless a deliberate doc/test-backed wording change is made.
- Pi, OpenCode, and Hermes plugin paths that consume dispatch/status/progress/report metadata use JSON where that metadata is available.
- Codex is treated as a skill/scaffold path, not a host plugin, and is checked only for docs/scaffold impact.
- Existing supported plugin functionality still works: dispatch ack, run tracking, timeout-derived watcher budgets, progress notifications/toasts, status/footer updates, session-report delivery, delivered/release bookkeeping, status/history/help/doctor/roles/stop surfaces.
- Root config and host integration assets are canonical; no parallel checked-in packaged fallback copies are maintained.
- `DECISIONS.md`, `ARCHITECTURE.md`, and `docs/plugin_creation.md` match the implemented behavior.
- Tests cover JSON contracts, default prose behavior, plugin JSON consumption, and asset/init behavior.

## Context / Assumptions

- Plugins already call the Python `orchestra` CLI for shared behavior.
- This work adds structured responses; it does not remove user-facing text output.
- Do not add compatibility fallbacks unless an existing supported path would otherwise break.
- Keep contract implementation simple, but complete for the plugin-facing paths being migrated.
- Subagent/LLM output remains untrusted text payload data. Core may include that text in JSON strings, but does not require subagents to produce JSON.

## Design Notes

Use command-local JSON flags, not a global mode:

```bash
orchestra status --json
orchestra do --json ...
orchestra _dispatch-ack --json ...
orchestra _progress-message --json ...
orchestra _await-run --json ...
orchestra _await-session-report --json ...
```

All JSON payloads should be valid JSON on stdout and avoid mixed prose on stdout. Diagnostic stderr may remain stderr.

Common fields:

```json
{
  "contract_version": 1,
  "kind": "status",
  "ok": true
}
```

Error fields where a command can return structured errors:

```json
{
  "contract_version": 1,
  "kind": "status",
  "ok": false,
  "error": {
    "code": "some_code",
    "message": "human-readable message"
  }
}
```

Do not make plugins parse `message` or `text` for control flow. Those fields are for display only.

## Required JSON Contracts

Exact field names can be adjusted during implementation if current app types already have better names, but the plan must cover these semantics.

### `orchestra do --json`

Needed by plugins for dispatch tracking and watcher budgets.

Required fields:

- `contract_version`
- `kind: "dispatch"` or `"dispatch_ack"`
- `ok`
- `run_id`
- `role`
- `status`
- `timeout_seconds`
- `message` or `text` containing the same human acknowledgement currently returned
- any existing fallback/effective harness fields already surfaced in prose, if plugins or tests rely on them

Default `orchestra do` prose remains unchanged.

### `orchestra status --json`

Needed by status/footer/run-id completion paths.

Required fields:

- `contract_version`
- `kind: "status"`
- `ok`
- `session_id`
- `active_runs.count`
- `active_runs.limit` when known
- `active_runs.runs[]` with at least `run_id`, `role`, `status`, `task_label`, and useful timestamps if already available
- `global_active_runs.count`
- `global_active_runs.limit` when known
- role counts used by Pi footer/status rendering

Default `orchestra status` prose remains unchanged unless separately approved/tested.

### `orchestra _dispatch-ack --json`

Needed where plugins currently ask core to render acknowledgement text.

Required fields:

- `contract_version`
- `kind: "dispatch_ack"`
- `ok`
- `run_id`
- `role`
- `message` or `text`

Default prose remains unchanged.

### `orchestra _progress-message --json`

Needed for non-prompt progress notifications/toasts.

Required fields:

- `contract_version`
- `kind: "progress_message"`
- `ok`
- `run_id`
- status/progress state currently represented by the helper, if available
- `message` or `text`

Default prose remains unchanged.

### `orchestra _await-run --json`

Needed by per-run watcher code.

Required fields:

- `contract_version`
- `kind: "await_run"`
- `ok`
- `run_id`
- final `status`
- `timed_out` or equivalent when timeout occurs
- display `message`/`text` if currently surfaced
- error/blocker/result fields already available and needed by plugin notifications

Default prose remains unchanged.

### `orchestra _await-session-report --json`

Already has a JSON path in current code; normalize it only as much as needed without breaking existing consumers.

Required fields after normalization:

- `contract_version`
- `kind: "session_report"`
- `ok`
- `run_ids` or preserve existing `runIds` if changing would break current OpenCode/Hermes tests
- `report`

If existing consumers already rely on `runIds`, either keep it or support both `runIds` and `run_ids` with tests. Do not churn this contract just for naming purity.

### Delivered/release helpers

`_mark-session-report-delivered` and `_release-session-report` only need JSON if plugins parse their output. If they are success/failure by exit code only, document that and leave them unchanged.

## Risks

- Breaking existing prose output: avoid by making JSON opt-in and testing default output for every touched command.
- Incomplete plugin migration: avoid by explicitly covering Pi, OpenCode, and Hermes; check Codex only as a skill/scaffold documentation path.
- Contract drift: avoid by centralizing envelope construction and testing exact required fields.
- Packaging/init regressions during asset cleanup: avoid by moving asset cleanup before plugin edits and verifying build/init behavior.
- Overengineering: avoid schema frameworks, version negotiation, or broad compatibility layers unless tests reveal a concrete need.

## Decisions Resolved

- `_await-session-report --json` keeps existing `runIds` as the public field and may add the common envelope around it only if existing consumers remain compatible.
- `--copy` remains supported. It copies from canonical root-derived assets, not from maintained checked-in fallback duplicates. If canonical assets are unavailable, init fails clearly.
